# Intermittent slow invocation investigation

## Status

Open, with two pre-`Main` delay components identified. One retained Windows Performance Recorder trace proves that Microsoft Defender synchronously scanned the unsigned deployed executable for 702.310 ms before Windows created the process. A second retained trace captured a 2455.128 ms launch composed of 1784.354 ms inside Windows process creation before Defender opened the executable, a 655.392 ms Defender scan, 7.079 ms from the scan completing to process creation, and 8.303 ms from process creation to managed `Main`.

An exact contextual Defender exclusion remains a useful partial mitigation, but it would have removed only 655.392 ms of the second occurrence. It cannot make invocation reliable by itself. The temporary scheduled task `TheCloser Launch Trace (Temporary)` remains registered. After removing minifilter stack capture to retain more early scheduling history, the task armed `.tmp/TheCloser-auto-20260828-204631.etl` with monitor PID 32076. The earlier report of an approximately 10 second launch has not been captured and may be an extreme instance of the pre-image process-creation mode or another mode.

The daemon IPC fix design was agreed on 2026-08-28 and is recorded in the fix design section below; implementation has not started.

## Symptom

- The first TheCloser activation after an idle interval can feel delayed. Reported cases range from noticeable sub-second pauses to about 10 seconds.
- Subsequent invocations usually feel instant.
- The behavior was not noticed at commit `04cbeb7` and appeared after later changes. No commit in that range has been isolated by bisect.
- The machine normally remains running continuously, but a reboot on 2026-08-28 exposed that an in-memory trace must be re-armed at logon.

## Confirmed observations

### Application work is not the dominant delay

The invocation probe receives a `QueryPerformanceCounter` value immediately before AutoHotkey calls `Run`, then records the first timestamp inside managed `Main`. Slow samples spend nearly all extra time between those boundaries. Once `Main` begins, daemon discovery, configuration, and window closing remain near their normal durations.

The daemon was alive in the captured slow samples. Moving logger file writes to a queue in `f668ff4` removed synchronous file logging from the invocation path, but slow launches still occurred.

### 2026-08-27 asymmetric sample

- Real Sync executable, PID 50320: `main-enter` at 625.501 ms; close returned at 706.695 ms.
- Local no-op executable, PID 16064: `main-enter` at 24.785 ms.
- The peer launch timestamp was 654.209 ms after the real launch timestamp, so the launches were not concurrent enough to prove a path-specific cause.

This sample established that the real invocation delay was before `Main`, but it did not establish that the Sync path caused the delay.

### 2026-08-28 near-concurrent two-path sample

- Real Sync executable, PID 8412: `main-enter` at 692.508 ms; main exited at 764.136 ms.
- Local no-op executable, PID 18092: `main-enter` at 684.043 ms.
- The launch timestamps were 51.133 ms apart.
- A preceding paired activation about 10 minutes earlier reached `Main` at 137.270 ms and 139.906 ms.

This sample proves that at least one near-concurrent slow occurrence affected both executable locations before `Main`. It does not prove that the same underlying cause delayed both processes. A Sync-only explanation cannot account for every occurrence. The paired copy no longer added enough diagnostic value and was retired on 2026-08-28; the kernel trace can identify path-specific waits directly.

### 2026-08-28 retained Defender trace

The automatic detector stopped on deployed process PID 26848 after measuring 715.924 ms from the AutoHotkey launch timestamp to managed `Main`. The retained trace is `.tmp/TheCloser-auto-20260828-182847.etl`; it covers 29 minutes and 18 seconds with no lost events.

The trace establishes this sequence:

- AutoHotkey opened the deployed `TheCloser.exe` image.
- Microsoft Defender started a real-time stream scan requested by AutoHotkey.
- Defender performed exhaustive scanning, low-fidelity signature checks, hash calculation, and trust validation.
- Defender recorded that `TheCloser.exe` was not trusted and that signed-file validation failed.
- The Defender stream scan stopped 702.310 ms after it started.
- Defender's process-create event for TheCloser followed 3.713 ms later, 706.023 ms after the scan began.
- Managed `Main` followed about 10 ms after process creation, matching the probe's total 715.924 ms pre-`Main` measurement.

The hard-fault and disk-I/O reports contain no events for the trigger interval. The minifilter-delay report contains no separate delay record. For this sample, Defender's synchronous scan accounts for nearly the entire observed pause and is the confirmed root cause.

After the trace had already stopped, deployed process PID 18440 recorded another 711.074 ms before `Main`, followed by launches at 14.221 ms, 11.741 ms, and 10.570 ms. Its duration and before-`Main` shape strongly match the captured Defender mode, but it has no retained kernel trace and is therefore corroborating evidence rather than independent proof.

### 2026-08-28 retained mixed process-creation and Defender trace

The automatic detector stopped on deployed process PID 14092 after measuring 2455.128 ms from the AutoHotkey launch timestamp to managed `Main`. The retained trace is `.tmp/TheCloser-auto-20260828-201856.etl`; it covers 18 minutes and 9.744 seconds with no lost buffers or events.

The AutoHotkey launch timestamp was mapped into ETW time through a minifilter event carrying a raw `QueryPerformanceCounter` value. The trace establishes this sequence:

- 1784.354 ms elapsed after AutoHotkey called `Run` and before Microsoft Defender received its first open of the deployed executable.
- Defender's real-time stream scan then took 655.392 ms. This was 26.694 percent of the total pre-`Main` time.
- Windows created the process 7.079 ms after the scan stopped.
- Managed `Main` began 8.303 ms after process creation.

The four intervals sum to the probe's complete 2455.128 ms measurement. There was no target executable file I/O before Defender's first open, so the first 1784.354 ms was not loader or storage work on `TheCloser.exe`. The hard-fault, disk-I/O, and minifilter-delay reports contain no independent delay in the trigger interval. A CPU export covering the interval shows the system approximately 90 percent idle.

The exact AutoHotkey v1.1.36.02 source was inspected at its official tag. `Script::ActionExec` calls `CreateProcess` first and uses `ShellExecuteEx` only if `CreateProcess` fails. The fully qualified executable invocation therefore does not normally pass through shell resolution. The unexplained first interval is inside the Windows `CreateProcess` path before the target image is opened.

The system collector retained context switches only from approximately 39 ms after the AutoHotkey launch timestamp because minifilter stack capture consumed the circular history. It therefore missed the launch thread's initial switch-out and cannot identify its precise wait reason. The next trace drops those already-unhelpful minifilter stacks while retaining the minifilter events.

## Hypothesis state

### Confirmed

- The intermittent delay can occur before any managed application logic runs.
- Window closing and configuration work are not the source of the long pause in the measured samples.
- The daemon can remain alive throughout a slow occurrence.
- One near-concurrent sample showed pre-`Main` delays in both the Sync executable and an identical local copy; whether they shared one cause remains open.
- Microsoft Defender's synchronous scan of the unsigned and untrusted executable caused the retained approximately 716 ms slow launch.
- A second retained launch contained both a 655.392 ms Defender scan and a separate 1784.354 ms delay inside Windows process creation before the executable was opened.
- AutoHotkey v1.1.36.02 normally implements `Run` with `CreateProcess`, so shell resolution is not responsible for the second trace's pre-image interval.

### Refuted or narrowed

- Synchronous logger writes are not required for the delay; they were queued off the invocation path and the symptom recurred.
- A Sync-only path explanation is not sufficient for all occurrences.
- The asymmetric 2026-08-27 pair cannot be treated as proof of a Sync-specific delay because its peer launch was issued after most of the real delay had elapsed.
- Windows did not create the captured process until the Defender scan completed, so application scheduling, loader work, daemon discovery, configuration, and window-closing logic cannot explain that sample's pause.
- Hard faults and storage I/O did not contribute measurable work in the captured trigger interval.
- A contextual Defender exclusion cannot eliminate every slow occurrence. It would have removed only 655.392 ms of the captured 2455.128 ms launch.
- ReadyToRun and JIT tuning do not address the captured delays because the deployed executable already uses Native AOT and reached managed `Main` only 8.303 ms after process creation. Native AOT size optimization might shorten some byte-scanning work, but it cannot remove the Defender scan or the pre-image `CreateProcess` wait.

### Open

- Why Defender repeats the scan after an idle interval despite the executable bytes remaining unchanged.
- Whether trusted code signing prevents or materially shortens the scan without requiring a Defender exclusion.
- What blocks AutoHotkey's `CreateProcess` call for 1784.354 ms before any open of the target executable.
- Whether the approximately 10 second report is an extreme instance of the same pre-image process-creation path or a distinct slow-launch mode.

## Selected direction

On 2026-08-28, the user selected daemon IPC as the fix direction. The goal is to avoid launching a new executable on the normal activation path, which removes both measured sources of variability: the Windows process-creation path and the synchronous Defender scan. An exact contextual Defender exclusion remains an optional partial mitigation, not the selected primary fix, and no Defender setting has been changed. The agreed design is recorded in the fix design section below.

The current 128 MB automatic WPR trace can remain armed while implementation proceeds. If it captures another slow launch before the IPC fix lands, preserve and analyze the ETL using the existing resume procedure. Once daemon IPC is deployed and verified, remove the scheduled task and temporary diagnostic code using the cleanup procedure below.

## Fix design: daemon IPC activation

Agreed on 2026-08-28. This section is the governing design for the fix.

### Operating context

- Deployment environment and operational criticality: a personal Windows desktop utility on the author's own machines, deployed by hand through a synced Bin folder. A failed activation means a window does not close, so the tool itself is not operationally critical.
- Audience: personal use (single user, own machines).
- Failure consequence and data or security sensitivity: no data is stored or transmitted. The process runs elevated, injects input, and mutates the system-wide foreground lock timeout, so the worst failures are desktop-wide: a stuck trigger button swallowing clicks, or the foreground lock timeout stranded at 0 until reboot. No security-sensitive surface exists beyond the established elevated invocation chain.
- Concurrency and compatibility risk: high for this change. Three cooperating processes share kernel objects and a memory-mapped file with crash windows inside the protocol, and elevation boundaries constrain who can signal whom.
- Reversibility and recovery cost: deploys are git-versioned and trivially reverted. The one hard-to-reverse state, the stranded foreground lock timeout, is the documented residual risk the design's repair machinery exists for.
- Expected feature lifetime: long-lived personal tool with a small codebase.

Derivation: audience category personal use gives baseline tier low. Uplift judgments, each recorded with its basis: deployment_criticality not fired (convenience tool; failure is a window that stays open); failure_consequence fired (elevated input injection and a system-wide setting give desktop-wide failure modes); concurrency_compatibility fired (multi-process kernel-object and shared-memory protocol with crash windows); reversibility_recovery not fired (versioned deploys, repairable state); expected_lifetime not fired (small personal codebase, debt surface small). Two fired uplifts raise low to high, the cap. Tier: high; per-dimension effort: validation high, recovery high, compatibility high, observability high, proof effort high.

### Activation flow

The normal activation path launches no executable. On a trigger press, the AutoHotkey script writes a small payload into the existing shared memory-mapped file and signals a new session-local named auto-reset event, `TheCloserActivationEvent`. The daemon's main loop becomes a `WaitAny` over the exit event and the activation event with the existing 5 second timeout; the timeout branch keeps the crash-repair watchdog unchanged. On activation the daemon samples the cursor itself and runs the close pipeline in-process. The daemon wakes in well under a millisecond, so the cursor cannot move meaningfully between the press and the sample; nothing position-related needs transmitting. That premise covers the idle branch. The complementary branch: a press arriving while a close is in flight leaves the auto-reset event signaled and is handled when the close returns. The throttle is evaluated there, at handling time, against the prior handler entry: a press collapsed into a close shorter than 200 ms is skipped, while one collapsed into a longer close survives the throttle and performs a second close at the cursor's position then. Both outcomes are accepted: today a press during a close is silently dropped by the guard mutex, so the deferred second close is a deliberate improvement that honors a real double-press, and the handling-time cursor sample represents the user's latest intent, where a press-time position would aim the close at a spot the user has already left. Press-time position transmission is an explicit non-goal.

Invocation is fire-and-forget. Nothing in the AutoHotkey layer can usefully consume an acknowledgment, and the fallback decision needs only the existence check described next. Two transports were considered and rejected in the design round: a named-pipe server carries payload and acknowledgments naturally but adds an accept-loop lifecycle with reconnection failure modes to buy an acknowledgment nothing consumes, and a window message to a hidden daemon window is AutoHotkey-native but forces a message pump, a second concurrency model, into a process with one blocking loop. The event-plus-MMF form reuses the two kernel-object patterns the codebase already has and keeps the daemon single-threaded.

Fallback: if `OpenEvent` fails for any reason (name absent because no daemon is running, or access denied in an unsupported mixed-elevation configuration), the script runs `TheCloser.exe` exactly as today. That press pays today's slow path but always works, and the launched app starts the daemon, so the next press is fast. `TheCloser.exe` remains a fully functional standalone entry point; its `Program.cs` control flow is unchanged, and the type moves change none of its using directives, since the file already imports `TheCloser.Shared`; its access to the moved internal types relies on the `InternalsVisibleTo` entries below.

Daemon-down detection is exact within the supported all-elevated chain, because named kernel events vanish when the owning process's last handle closes: there the name exists exactly while the daemon lives, so `OpenEvent` failing cannot false-positive. In the unsupported upward mixed-elevation direction an access-denied open reads as down and takes the fallback, which is the designed degradation (see the elevation paragraph). To preserve that property the script opens and closes every handle per press and never caches one; a cached handle in the long-lived AutoHotkey process would pin the object past the daemon's death, breaking both the detection and the invariant that named MMFs vanish with their last handle. A hung (not dead) daemon still holds its event, so a press signals successfully and is lost; that is the same exposure class as the current hung-daemon MMF pin, and the watchdog's per-iteration exception isolation keeps it unlikely.

### Shared state layout and message contract

The MMF (`TheCloserSharedState`, 1024 bytes) gains an activation payload region. Complete layout and every consumer's handling:

| Offset | Size | Field | Writers | Readers |
|---|---|---|---|---|
| 0 | 8 | Throttle tick (`Environment.TickCount64`) | App on fallback runs; daemon on IPC activations | App and daemon; both paths throttle each other, threshold 200 ms unchanged |
| 8 | 4 | Repair flag | `ForegroundLockSuppression` publishes the record; `TimeoutRepair`/`CrashRepair` restore and clear, via both paths | Both paths; semantics unchanged |
| 12 | 4 | Saved foreground lock timeout | Same as repair flag | Same as repair flag; semantics unchanged |
| 16 | 8 | Launch QPC (raw `QueryPerformanceCounter` at press time) | AutoHotkey, before signaling; the daemon zeroes it at handler entry (consume-once) | Daemon, for the per-activation latency log line only. The fallback path does not read it; the app keeps receiving its QPC via the existing `--probe-launch-qpc` argument |
| 24 | 4 | Trigger button code (0 = unknown, 1 = XButton2) | AutoHotkey, before signaling; the daemon zeroes it at handler entry (consume-once) | Daemon, for logging only, and deliberately consumed by no logic. Recorded for log forensics (the stuck-XBUTTON2 incident postmortem hinged on knowing which button triggered) and for future bindings at near-zero cost. `TriggerButtonHealer` does not consume it; the healer monitors its fixed middle/X1/X2 set regardless |

The event signal is the payload-ready flag: the script writes values, then calls `SetEvent`, and the daemon reads only after waking, mirroring the value-before-flag discipline the repair record already documents. Two rapid presses can overwrite the payload before the daemon reads it; that is last-writer-wins and harmless because the 200 ms throttle makes the earlier press a no-op. The auto-reset event collapses N presses into one pending wake, matching today's semantics where extra launches exit on the throttle.

Latency logging: the daemon logs elapsed time from the payload QPC to handler entry on every activation. This permanently replaces what the temporary `InvocationProbe` measured on the IPC path and is the fix's verification instrument. Empty and implausible branch: if the QPC value is zero (payload never written or already consumed), non-positive, in the future, or implies a latency above 10 seconds, the daemon logs the activation with latency unavailable instead of a number. The payload is consume-once: after reading both fields at handler entry, the daemon zeroes them, so a later press whose mapping fails reads zero and logs unavailable rather than replaying the previous press's values (without the zeroing, a stale QPC newer than 10 seconds would pass every plausibility clause and log as a real latency). The payload is also trusted as a unit: when the QPC reads unavailable, the daemon logs the button code as unknown too. One benign race is accepted: an AutoHotkey payload write can land between the daemon's read and its zeroing, in which case that press's own wake reads zero and logs unavailable while the close itself proceeds normally. A logged button code of 0 is therefore observable before the first successful payload write of a daemon's lifetime, after a failed mapping, and in that race. Deferred presses are attributed structurally: the daemon keeps a handler-exit timestamp as a raw `QueryPerformanceCounter` value (`Stopwatch.GetTimestamp`, the same clock as the payload QPC, so the comparison is same-unit; daemon-lifetime, in-memory, initialized to the daemon's own start time and refreshed at every handler exit, skip outcomes included), and an activation whose plausible QPC predates that timestamp was collapsed behind the previous handling, so its line carries a deferred marker alongside the same number. The marker is judged only for a plausible QPC: an unavailable payload logs unavailable with no deferred judgment, since attribution needs a valid press time. Genuine IPC delay and queued-behind-a-close time therefore never blur in the durable instrument.

### Responsibility placement

Every responsibility of the current app `Main`, and where it runs on each path:

| Responsibility | IPC path (daemon) | Fallback path (app) |
|---|---|---|
| Guard mutex | Acquired with `WaitOne(0)` around each close; busy means a fallback instance is mid-close, so the press is skipped and logged. `AbandonedMutexException` counts as acquired. Released before healer dispatch, mirroring the app's release-before-linger. The handle's per-activation lifetime is finally-scoped (a `using`/`finally` around the whole close), so a throwing close still releases ownership and disposes the handle; it is never cached: a live cached or leaked handle would make `CrashRepair`'s `createdNew` liveness check read false on every watchdog tick and silently disable the watchdog. Per-activation create-unowned-then-`WaitOne(0)` is a genuine acquire, satisfying the acquired-not-probed invariant `CrashRepair` documents; `CrashRepair`'s own `initiallyOwned` idiom is unchanged | Unchanged |
| Pending-repair restore | After acquiring the guard mutex, if a repair record is pending, restore it before closing (mirrors the app's startup restore; holding the mutex prevents races). The watchdog branch additionally covers it every 5 s as today | Unchanged |
| 200 ms throttle | Read tick, skip and log if within threshold, else write tick and proceed. The threshold constant moves to `Constants` so both paths share it | Unchanged |
| Daemon ensure and pin wait | Not applicable | Unchanged |
| Configuration | Loaded once at daemon start with `reloadOnChange: true`; see configuration section | Unchanged (fresh read per run) |
| Close pipeline (`WindowCloser`, `ForegroundActivator`, `ForegroundLockSuppression`, timeout repair) | Runs in-process, exception-isolated per activation so a failed close never kills the daemon | Unchanged |
| Trigger-button healing | Dispatched as a background task after an attach-performing close so the up-to-2 s linger never blocks the next activation; the task body wraps the heal in the same log-and-swallow isolation as the close pipeline, so a failed heal logs its exception instead of faulting an unobserved task. Overlapping healer tasks are new concurrency this design introduces: today a lingering app instance's live guard-mutex handle makes a follow-up launch exit on the `createdNew` check, so healers never overlap in practice. Overlap is safe: a healer injects a release only for a button still observed down at its deadline, and a duplicated release for an already-up button is an OS-level no-op | Unchanged |

The daemon loop stays single-threaded: the watchdog iteration and the activation handler are branches of one `WaitAny` loop, so the guard mutex is acquired and released on one thread. The new concurrency is the healer task plus the configuration reload callback, which runs on a watcher thread and touches only the configuration root and the logger. All three consumers of that shared state tolerate it: the pipeline reads the last-good snapshot, never the live root; the logger is contention-tolerant by design; and the loop thread's per-activation snapshot build reads the live root under an accepted benign race recorded in the Configuration section.

### Code layout

These types move from `TheCloser` to `TheCloser.Shared` (which already targets the windows TFM and is AOT-compatible). Relocation rather than a daemon-to-app project reference is forced by the graph: the app already project-references the daemon so its exe lands in the app's output directory, and a reverse reference would close a cycle; `TheCloser.Shared` is the only acyclic shared home. The moved types: `WindowCloser`, `ForegroundActivator`, `IForegroundActivator`, `INativeWindowApi`, `NativeWindowApi`, `NativeMethods`, `ProcessSettingsParser`, `ProcessSettings`, `TitleBarClickPosition`, `TriggerButtonHealer`. `TheCloser` keeps `Program` and `InvocationProbe`. Each moved type keeps its current visibility; `TheCloser.Shared` gains `InternalsVisibleTo` entries for `TheCloser` and `TheCloser.Daemon` alongside the existing `TheCloser.Tests` entry. The package references `GregsStack.InputSimulatorStandard`, `Microsoft.Extensions.Configuration`, and `Microsoft.Extensions.Configuration.Json` move from `TheCloser.csproj` to `TheCloser.Shared.csproj`; the app and daemon consume them transitively.

`TriggerButtonHealer`'s header comment currently states it is deliberately app-hosted with no daemon backstop; that rationale is superseded and the comment must be rewritten in the move to describe the two hosting paths.

`TheCloser.Shared` gains the activation-handler unit, with the daemon as its only production consumer, shaped for testability with injectable delegates and GUID-suffixed kernel object names, following the existing `CrashRepair`/`TimeoutRepair` seam pattern; hosting it in `TheCloser.Shared` rather than the daemon keeps the existing `TheCloser.Tests` `InternalsVisibleTo` the only wiring the activation-handler unit tests need; the test project already references `TheCloser.Shared`, and no reference to the daemon, a `WinExe` AOT target, ever needs adding. New constants (`ActivationEventName`, button codes, the shared throttle threshold) go to `Constants.cs`. The payload offsets join the existing private offset constants inside `SharedState`, since offsets are an implementation detail of the accessor, and the existing offsets stay where they are; new accessors follow the existing accessor discipline.

The daemon constructs the close pipeline fresh per activation: a new `WindowCloser` with its `ForegroundActivator`, and a new healer instance when dispatched. Only `SharedState`, the configuration root, the last good configuration snapshot, the handler-exit timestamp behind the deferred marker, the healer tracking collection, the logger, and the daemon's own kernel objects (the MMF pin, the activation and exit events, the daemon mutex) live for the daemon's lifetime; the guard-mutex handle is per-activation, per the responsibility table. The attach-performed flag is sticky for a pipeline instance's life, so a daemon-lifetime instance would dispatch the healer after every close forever once a single attach had happened.

One piece of OS-level state outlives per-activation construction: `AttachThreadInput` pairs the loop thread's input queue with the target's, and the current implementation re-resolves the target thread from the window handle at detach time, so a window destroyed mid-close makes the detach a silent no-op. In the short-lived app that leak dies with the process within seconds; on the daemon's long-lived loop thread it would accumulate across activations, merging input queues desktop-wide. The move therefore hardens the detach: `ForegroundActivator` captures the peer thread ids at attach time, detaches by the captured ids, and logs a failed detach return instead of discarding it. The `INativeWindowApi` seam changes accordingly: its attach member returns the attached thread ids and its detach member takes them, replacing the current window-handle-resolving detach, with `NativeWindowApi` and `NativeMethods` following. This removes the design's dependency on any unprobeable claim about attachment lifetime after window destruction, because the pair detached is always exactly the pair attached; daemon-lifetime OS state stays limited to the objects enumerated above.

### Invocation layer (TheCloser.ahk)

The script gains `#SingleInstance Force` so any manual or overlapping start silently replaces the running instance instead of popping the replace dialog.

Auto-execute section: on script start, run `TheCloser.Daemon.exe --stop` with `RunWait`, awaiting the stopper process's own exit before anything else, then poll up to 5 seconds for the daemon mutex to vanish (comfortably above the roughly 2 second worst-case healer drain plus an in-flight close), then run `TheCloser.Daemon.exe --start`. The await is load-bearing, not a nicety: an asynchronous stop would race the starter through the highly variable process-creation window this file measured at 0.7 to 2.5 seconds, and a stopper landing after the fresh daemon starts would find the new exit event and kill it, leaving the machine daemonless right after logon; awaiting the stopper's exit guarantees no stop signal can arrive after the poll begins. The retry on the expiry branch awaits its `--stop` the same way. After the `--start`, poll up to 5 seconds for the daemon mutex to appear, sized above the 0.7 to 2.5 second process-creation window this file measured; if it has not appeared by then, continue in the same degraded mode as below. The expiry deliberately does not distinguish a daemon that died during startup from one still launching, and needs not: the degraded mode is not latched, every press's `OpenEvent` checks fresh, so a late-published daemon serves the next press, while a genuinely dead one is diagnosed from its own log rather than by the script. Expiry branch: if the mutex still exists at the stop deadline, run the stop-poll-start sequence once more; if that also expires, proceed without a daemon. That degraded state is self-healing: while the stale daemon is still draining, its activation event remains alive, so presses landing in that window signal a loop that has already exited and are lost (the same exposure as a hung daemon, bounded by the drain); once it exits, the event vanishes, each press takes the fallback, and the first fallback press after exit starts a fresh daemon (while the dying process lingers, the fallback app's daemon probe sees it and skips spawning, costing only the pin wait). Launch-failure branch: if either `Run` cannot launch the executable at all (the binary missing on a not-yet-synced machine, or a blocked image), the script suppresses AutoHotkey's error dialog (`UseErrorLevel`), since a modal at logon would block the headless auto-execute, and continues without a daemon: the same degraded mode as poll expiry. One bound on the self-heal claims: when the daemon binary itself cannot initialize, the degraded mode persists until that cause clears, with each fallback press retrying the start; that equals today's per-press baseline and is accepted. Stop-then-start rather than a bare idempotent start covers the upgrade transition: a daemon from an older deployment, which never creates the activation event, would otherwise hold the single-instance mutex, make every `--start` exit immediately, and silently pin every press to the fallback until reboot. On a machine that receives new binaries through the synced folder, the swap happens at the next logon, when the task restarts the script. The same sequence replaces an unelevated daemon left behind by manual testing (see the elevation paragraph below). Elevation is inherited from the elevated script, and the launch cost lands at logon or deploy time, off the press path. This removes the one remaining routinely slow press (the first press after logon or deploy, which would otherwise take the fallback), with one bounded residual: a press landing inside the auto-execute's own stop-poll-start window, a few seconds around logon or deploy, still finds no activation event and takes the fallback. That residual is accepted; it requires pressing within seconds of a logon or deploy.

The trigger handler, in order: capture QPC; `OpenEvent` with `EVENT_MODIFY_STATE`; on failure, run `TheCloser.exe` with the existing `--probe-launch-qpc` argument exactly as today and return (a launch failure there keeps today's modal error surface: an interactive presser is present to see it, and exposure is never worse than shipped, so the auto-execute's suppression rationale deliberately does not transfer); otherwise `OpenFileMapping` with `FILE_MAP_WRITE` plus `MapViewOfFile`, `NumPut` the QPC at offset 16 and button code 1 at offset 24, unmap and close the mapping; `SetEvent`; close the event handle. If the mapping unexpectedly fails while the event opened, skip the payload writes and still signal: the daemon then closes normally and, because the payload is consume-once and was zeroed at the previous read, logs latency unavailable. One narrow race is accepted: the daemon can exit between `OpenEvent` and `SetEvent`, dropping that press; the window is microseconds and the next press falls back. The script thereby becomes a second, hand-synchronized holder of the activation event name, the MMF name, the payload offsets, the button code literal, and the daemon mutex name (which the auto-execute poll observes): a deliberate cross-language duplication, since AutoHotkey cannot consume `Constants.cs`, called out by a comment at each site in all three holders (`TheCloser.ahk`, `Constants.cs` for the names and button codes, `SharedState.cs` for the offsets), the auto-execute poll site included; the project CLAUDE.md's kernel-object centralization note gains the script as its one non-C# copy during the docs pass. The per-press never-cache-a-handle rule extends to the auto-execute poll: each poll iteration opens the daemon mutex only to test existence and closes it before sleeping, and every branch (vanished, expiry, launch failure) ends with no handle held, since a script-held daemon-mutex handle would pin the name past the daemon's exit and permanently block every later `--start` on its single-instance check.

Elevation: the deployed chain keeps every party elevated (elevated script; daemon inheriting elevation through the auto-execute launch or the fallback launch). Mixed-elevation scenarios split by direction. Upward, an unelevated script against an elevated daemon, `OpenEvent` fails with access denied and the press takes the fallback. Downward, an elevated script against an unelevated daemon left behind by manually starting one from an unelevated shell, `OpenEvent` succeeds, so presses route to a daemon that cannot close elevated windows and no fallback fires; detecting this per press is an explicit anti-goal, because it arises only from manual meddling in a deployed chain, and the stop-then-start auto-execute replaces any such daemon at the next script start.

### Daemon lifecycle

- Startup order: pin the MMF, create the activation and exit events, publish the daemon mutex last. The mutex remains the pinned-and-ready proof for the app's pin wait, and publishing it last makes it prove more: every object a press or a `--stop` needs already exists once the mutex is visible, so a stopper that finds the mutex always finds the exit event, closing the silent-drop window that a mutex-before-exit-event order would leave between publish and event creation. The events existing slightly before the loop enters `WaitAny` loses nothing: an auto-reset event holds its signaled state until waited on.
- A second daemon instance briefly co-owns both auto-reset events, then exits on the existing single-instance mutex check and closes its handles; harmless.
- Graceful shutdown via `--stop` and the exit event is unchanged, except for two additions. First, after leaving the loop the daemon runs one final repair tick under the same log-and-swallow exception isolation as a watchdog iteration, so a throw is logged and the drain and unwind always still run; the tick is safe by construction because the repair proceeds only when the guard mutex is acquirable, so a pending foreground-lock repair record never dies with the MMF pin on a graceful stop, and a tick that throws leaves the record for the fallback app's startup restore. This matters because the auto-execute makes graceful stops routine, and it absorbs the final-repair-tick half of the "Deploy stops the daemon with a hard kill" quick win. A record whose guard mutex is held at that tick belongs to the holder's own restore path. Second, the daemon drains healer tasks before disposing its logger. Ordering: the drain runs inside the daemon's run scope, before the using-scope unwind releases the daemon mutex, the activation and exit events, and the MMF pin and disposes the configuration root (unregistering its reload watcher), and the logger is disposed last; the daemon mutex therefore vanishes only after the drain completes, which is the premise of the auto-execute poll budget. A reload callback firing during shutdown either logs normally or arrives after logger disposal, where the logger's post-dispose no-op drops the line silently: an accepted loss of at most one warning at shutdown. The tracking collection's complete lifecycle: a healer task is added on dispatch, removes itself on completion, and the container is thread-safe, since completions land on thread-pool threads while the loop may be adding. At shutdown the daemon snapshots the collection and awaits the snapshot. Healers run concurrently and each is bounded by its own 2 second deadline, so the collection's steady-state size is zero or one and shutdown lags by at most about 2 seconds; no in-flight heal is cut off or left logging into a disposed logger.
- Daemon killed mid-close: the repair record dies with the daemon's MMF pin, stranding the foreground lock timeout until reboot if the kill lands inside the sub-second SPI window. The same kill also cuts off any in-flight healer task, which can leave a trigger button stuck down until manual recovery (the stuck-XBUTTON2 entry in BUGS_HISTORY.md records the recovery command), mirroring today's exposure when a lingering app instance is killed mid-heal. Both consequences are the same class as the accepted residual risk already documented in CLAUDE.md (app killed while no daemon pins), with the roles swapped, and are accepted alongside it. The common failure, an exception inside the pipeline, is handled in-process and restores normally.

### Configuration

The daemon builds the same `ConfigurationBuilder` as the app but with `reloadOnChange: true`, giving `FileSystemWatcher`-driven hot reload with the existing manual section parsing, which is what keeps the path AOT-clean (no reflection binding, no options/DI packages). The per-activation re-read alternative (a fresh build or last-write-time comparison each press) was considered and kept only as the recorded fallback below: the watcher amortizes parse cost off the press path for a file that rarely changes, while preserving the same edit-then-next-press semantics. Edits to `appsettings.json` take effect from roughly a quarter second after the write, preserving today's edit-then-next-press-works behavior. Failure branch: a reload that observes a malformed or half-written file must not change dispatch behavior or kill the daemon. The builder sets `FileConfigurationSource.OnLoadException` to log the failure and mark it handled; that handler covers parse failures only, since the provider opens the file outside its handled region, so a file-open failure (the file held or mid-replace by the sync client) instead faults the framework's discarded watcher task: the process survives, no line is logged, and the provider keeps its previous data. A parse failure leaves the provider empty until a later successful reload, and the last-good snapshot covers dispatch through either shape. The daemon then snapshots per activation: it enumerates the live root's complete path-value pairs (`AsEnumerable()`, which covers both the flat-string and nested-object entry forms the README documents), and when the enumeration is non-empty it rebuilds an in-memory `IConfigurationRoot` from those pairs (`AddInMemoryCollection`) as the last-good snapshot. The snapshot is a value copy, never retained `IConfigurationSection` references, which are live views over the reloading providers and would go empty with the root. One further benign race is accepted: the snapshot build's enumeration can overlap a watcher reload and adopt a mix of pre-edit and post-edit pairs; the blast radius is one close dispatched under that mixed configuration, and the next activation's snapshot self-heals, mirroring the bounded payload-write race documented in the layout section. The close pipeline always receives the last-good snapshot through its unchanged `IConfiguration` seam, never the live root, so an empty root after a failed reload leaves dispatch on the previous good configuration with a logged configuration-reload warning. The snapshot joins the daemon-lifetime state named in Code layout, and reload failures self-heal at the next successful reload. Initial state: the snapshot starts as the empty configuration; before the first non-empty read (a machine with no `appsettings.json`, or a first load the handler swallowed), the pipeline receives the empty snapshot and `ProcessSettingsParser` resolves every process to its defaults, exactly today's behavior without the file. The warning is reserved for empty-where-previously-non-empty; a never-populated snapshot fires none. (live-claim: provisional) The reload watcher's reliability on the synced deploy folder is unverified; if it proves flaky during implementation, the agreed fallback is a last-write-time comparison per activation, reloading only on change. Pass condition: during end-to-end verification, edit `appsettings.json` while the daemon runs and observe the next activation, at least 2 seconds later, dispatch per the edited setting; two consecutive misses adopt the fallback. The same check also overwrites the file with malformed JSON and verifies the daemon survives, logs the reload warning, and keeps dispatching from the last good snapshot, then restores the file and verifies recovery; it additionally exercises the open-failure shape against the AOT-published daemon (hold the file exclusively while touching it, and delete-and-rename it as the sync client does), verifying the daemon survives both and the next activation still dispatches from the last good snapshot, with the open-failure branch expected to log nothing.

### Deployment

`deploy.ps1` takes over invocation-layer restarts so AutoHotkey script changes no longer require manually re-running `install-elevated-ahk.ps1`:

- After copying files, if the scheduled task `TheCloser AutoHotkey (elevated)` exists: `Stop-ScheduledTask`, then poll the task's state until it leaves `Running` (bounded at 10 seconds), then `Start-ScheduledTask` (fresh elevated instance reading the just-copied script, whose auto-execute section also starts the freshly deployed daemon), then poll within 5 seconds for the task's state to return to `Running`. Task-level identity deliberately sidesteps process inspection: an unelevated shell cannot read an elevated process's command line (`Win32_Process` returns it null), so any command-line check would never match and would abort every deploy under the fail-loudly rule; the stop-poll already proved the old instance ended, so a `Running` state after the start proves a fresh instance. A failed poll on either side fails the deploy with a nonzero exit rather than reporting success. Stop-then-start is required rather than a bare start because the task runs with the default `IgnoreNew` multiple-instances policy and its logon instance stays running indefinitely, so a bare `Start-ScheduledTask` would be silently ignored. A discarded start is excluded structurally rather than detected: `IgnoreNew` can only discard a start while an instance runs, and the stop-poll proves no instance runs before the start is issued; the post-start poll then catches the remaining failure shape, a start that never brings the task back to `Running`. (live-claim: provisional) That an unelevated shell may stop and start a Highest-run-level task it owns is verified for start by established practice but unverified for stop; if stop requires elevation, the fallback is folding the stop and start into the same self-elevated child that already handles the stubborn daemon stop, costing one UAC prompt per deploy. Pass condition: the first deploy after implementation runs the stop-poll-start sequence from an unelevated shell and the post-start state poll observes the task leave and re-enter `Running`; an access-denied stop adopts the fallback.
- If the task does not exist (first deploy on a machine): self-elevate a child that runs the deploy target's copy of `install-elevated-ahk.ps1` (after the copy step, so the registered task binds to the deployed script; the installer's `$PSScriptRoot`-relative `-AhkScriptPath` default would otherwise bake the invoking copy's location into the task), reusing deploy's existing elevation pattern with `-Wait`. The deploy then verifies the branch the same way as the task-exists branch: the task must exist and its state must reach `Running`; a missing task or a state that never reaches `Running` fails the deploy with a nonzero exit, so a failed or dismissed elevation cannot report success with no invocation layer installed. One UAC prompt, once per machine. This branch is verified once per machine by that first-deploy observation and deliberately not re-exercised afterwards, a stated verification exception rather than an unpinned rule.

`install-elevated-ahk.ps1` drops the `-StartNow` switch and performs unconditionally: register the task, stop the task if it is running (its logon instance would otherwise make the later start a silent no-op under `IgnoreNew`), sweep away every AutoHotkey instance running the script by command-line leaf match, task-hosted or not (the sweep covers instances launched outside the task or from a differently pathed copy of the script, which `#SingleInstance Force`'s same-path replacement would miss; this carries forward the old `-StartNow` block's replace-without-logoff rationale), then start the task and poll within 5 seconds for its state to return to `Running`; the stop half is likewise polled until the state leaves `Running`, bounded at 10 seconds, before the sweep and start, since a start issued while an instance still runs is silently discarded under `IgnoreNew`. A failed poll on either side fails the installer with a nonzero exit. The installer runs elevated and could inspect processes, but it uses the same task-state target as the deploy for uniformity. The deploy's task-exists branch deliberately has no sweep: on a machine already running the deployed chain, the only instance to manage is the task-hosted one its stop-poll already ends. It keeps shipping to the deploy target for use on other machines.

No forced sequence: the re-scope is a text edit that can land any time after this design ships.
- "Logger rotation only runs at construction": moving per-press logging, the latency instrument included, into the daemon makes the daemon's log (which today rotates only at construction) the instrument's home, so that quick win becomes an upstream dependency of this design's observability; land it before or together with this design. - "App launch during a daemon repair tick is misclassified": that entry's premise, that the daemon holds the guard mutex only in a microseconds-wide repair window, widens under this design, which holds the guard mutex for whole daemon closes; a manual or racing fallback launch during a daemon close now exits on `createdNew` for the close's full duration. The remaining active entries reference relocated types only by symbol name, which survives the move per that file's own anchoring convention; no other entry makes a claim this design invalidates.

### Verification criteria

- Daemon latency log passes when each of 10 consecutive normal activations (IPC-path activations carrying a plausible logged latency and no deferred marker; latency-unavailable lines are excluded, since they carry no number to judge) shows press-to-handler latency at or below 20 ms, and at least three of the ten are first presses after an idle interval of 30 minutes or more: the symptom lives in the after-idle population (warm back-to-back presses were never slow), so a warm-only sample cannot falsify the fix. Today's slow mode measured 716 to 2455 ms before `Main`. The event wake itself is sub-millisecond; the 20 ms bar allows for AutoHotkey DllCall overhead and scheduling jitter.
- IPC-path closes work e2e; fallback-path closes work with the daemon stopped; a press with the daemon stopped starts it for the next press.
- A deploy with an edited `TheCloser.ahk` results in the new script running elevated with no manual step.
- An AHK script restart replaces a running daemon: the daemon log shows the old instance stopping and the new instance starting, covering the upgrade transition where a stale daemon would otherwise pin presses to the fallback.
- The invocation-layer rules are exercised once during the e2e pass: a second script start while one runs is silently replaced (`#SingleInstance Force`); an auto-execute run against a temporarily renamed daemon binary continues into the degraded mode without a dialog; the deploy's fail-loudly rule is standing coverage rather than a one-time check (the stop-poll and post-start poll run on every deploy, so a start that never restores `Running` surfaces as a nonzero deploy exit the first time it ever happens); the rewritten installer is exercised once by running it against a registered-and-running task with one additional script instance started outside the task from a differently pathed copy of the script (a same-path decoy would be replaced by `#SingleInstance Force` and vacate the setup; the differently pathed copy is also exactly the case the sweep exists to cover), observing the stop-poll end the task-hosted instance, the sweep end the outside-task decoy, the start-poll succeed, and a single fresh task-hosted instance survive at a zero exit (an instance-free run would exercise the sweep only vacuously); and an auto-execute run against a deliberately held daemon mutex (an out-of-process holder in the shape of the existing `HoldLogMutex.ps1` fixture) retries the stop-poll-start sequence once and then continues into the degraded mode; the fixture then exits, closing its handle so the name vanishes (releasing ownership alone would keep the name alive), and the next press's fallback launch must produce a running daemon, which pins both the no-handle-held rule on the expiry branch (a script-leaked handle would keep the name alive and block the start) and the degraded mode's self-heal.

## Resume procedure

When the user reports another slow activation:

1. Read `.tmp/wpr-auto-stop-output.txt`. If present, preserve the named ETL and note the trigger PID and duration here.
2. Read the final probe records from `%TEMP%\TheCloser.Probe.log` and correlate the PID with the ETL.
3. Analyze process lifetime, loader and hard-fault events, thread scheduling, file and minifilter delays, and Defender events for the interval from the AHK launch timestamp through `main-enter`.
4. Record evidence and update the hypothesis sections before proposing a fix.
5. If no ETL was saved, check the scheduled task, WPR status, reboot time, and monitor status before changing the detector.
